# Doom Agent

Doom Agent is intended to be a local-first personal system agent that lives
inside DoomArch. It is not a chatbot added on top of the desktop.

Its purpose is to understand the owner's environment, help operate the system,
work with local projects and information, and eventually provide a persistent
intelligent presence through the DoomArch Shell.

## Principles

### Local-first

Doom must remain useful without an Internet connection or paid AI service.
Remote models may provide optional additional capability, but they must not
become a requirement for Doom to exist.

Models are replaceable components. They are not Doom itself.

### Owner-centric

Each Doom installation belongs to its own owner.

Personal identity, memories, voice data, credentials and other private state
must never be embedded in the public DoomArch repository. A fresh installation
should establish its own owner and learn about them progressively.

Voice recognition may contribute to identity but must not by itself grant
unrestricted authority.

### Capability-based

Doom should operate DoomArch through explicit, structured capabilities rather
than unrestricted shell access.

Examples may eventually include:

- audio state and control
- network and Bluetooth management
- Hyprland workspaces and windows
- systemd inspection
- application launching
- project and file search
- Git inspection

Capabilities should define validation, permissions and confirmation requirements
independently of the model using them.

### Observable and controllable

The owner should be able to understand what Doom knows, what it can access and
what actions it can perform.

Memory and permissions should be inspectable and removable rather than hidden
inside an opaque agent.

### Portable core, private identity

Doom's architecture, capabilities, shell integration and portable configuration
belong in DoomArch and may be distributed through Git.

Owner identity, memories, secrets and machine-local state remain private and
outside the repository.

## Architecture direction

DoomArch is currently expected to evolve around three cooperating pieces:

- **DoomArch Shell** — the visual and interactive presence of the system.
- **Doom Runtime** — deterministic local capabilities for observing and
  controlling DoomArch.
- **Doom Agent** — reasoning, context, memory and orchestration built on top of
  those capabilities.

The shell and agent may both consume Doom Runtime capabilities. The agent should
not need to know implementation details such as individual PipeWire commands.

## Themes

Doom Agent may eventually assist the owner in creating and modifying DoomArch
themes interactively.

Themes should remain declarative and understandable rather than becoming opaque
sets of files generated by an AI. A future theme system may describe shared
visual tokens, assets, geometry and motion and adapt them to components such as
Quickshell, Hyprlock, notifications and, where safely appropriate, system or
boot surfaces such as rEFInd.

The owner remains responsible for subjective design decisions; Doom can perform
the mechanical translation and iteration.

## Current scope

Doom Agent itself is not being implemented yet.

During early DoomArch development, new system capabilities should be designed
with future structured access in mind without prematurely forcing every backend
behind an abstraction layer.

The first planned step is a small Doom Runtime experiment with deterministic,
structured system capabilities and no language model.



### First functional spike

The first Doom Agent spike has completed an end-to-end local action:

owner language → local model → structured tool call → runtime validation →
capability dispatch → system backend.

Qwen3 0.6B Q4_0 through llama.cpp is currently used only as an experimental
local brain. The model is replaceable and is not part of Doom's identity.

The agent uses structured tool definitions derived from Doom capabilities rather
than unrestricted shell execution. Runtime validation remains authoritative:
model-generated calls that violate capability contracts are rejected before
execution.

On the current laptop, keeping the model server resident consumes too much
memory relative to the available 8 GB. The brain should therefore be treated as
an on-demand resource while the lightweight Doom Runtime remains independently
available. This lifecycle policy may differ on future hardware.
